# Связь без отдельного сервера

Актуальное решение после уточнения владельца: HTTP-агент из первоначального
наброска заменён встроенной записью в SQLite и каналом stdin/stdout.

```text
Процесс бота aiogram
  middleware → ограниченная очередь → фоновый поток → bot-<Telegram ID>.sqlite3
                                                           ↑ чтение SQLite WAL
Приложение Electron ↔ JSON lines по stdin/stdout ↔ дочерний Python bridge
```

На Linux сервере bridge запускается через `ssh -T`, а JSON передаётся
по стандартным потокам этой SSH-сессии. Проброс TCP-портов не нужен.
SSH является способом доступа к серверу; нового сетевого сервиса приложение не создаёт.

Именованные каналы Windows и Unix-сокеты Linux потребовали бы отдельного постоянно
работающего получателя, если события должны сохраняться при закрытом приложении.
Файлы SQLite одновременно решают доставку и долговременное хранение. WAL позволяет
читателю получать согласованный снимок при работающем писателе. При недоступной
папке библиотека повторяет запись с задержкой и ограничивает очередь.

Каждый бот имеет свой файл, чтобы разные боты не конкурировали за один writer lock.
Несколько экземпляров одного Telegram-бота разделяют файл и имеют разные сессии;
при занятости SQLite запись повторяется. Событие идентифицируется Telegram update ID,
повторная доставка не увеличивает счётчики. Хранилище содержит минимальные события,
а не тексты сообщений или исходные updates. Пользовательские ID сохраняются как
HMAC с отдельным секретом каждого бота для точного подсчёта уникальных за диапазон.

Bridge существует только пока работает приложение. Он читает базу, применяет
настройки и очистку, но не нужен ботам для сбора. EOF закрывает процесс.
SDK не устанавливает соединения с bridge и не запускает слушающие сокеты.
При закрытой панели очистку своих данных выполняют работающие боты.
При открытии панели очищаются также данные остановленных ботов.

С версии 0.3.0 этот же транспорт поддерживает управление процессами.
SDK получает адресованные его сессии команды через SQLite, а bridge запускает
конечный launcher для подготовительных шагов и основной программы. Дополнительного
сетевого сервиса нет. Профили, блокировки операций и статусы хранятся отдельно
в `process-control.sqlite3`. См. [описание управления](process-control.md).

## Условия

- Все боты и читатель используют одну папку `BOTCONTROL_HOME` на локальном диске сервера.
- По умолчанию используются папки текущего владельца. При разных OS-аккаунтах
  владелец задаёт общую папку и права для этих аккаунтов самостоятельно.
- SQLite WAL нельзя использовать как общий файл по SMB/NFS. При SSH база читается
  на сервере, на компьютер владельца передаётся только JSON.
- Доступ контролируется правами ОС. Отдельного API-токена или веб-авторизации нет.
- Полная потеря диска или аварийное завершение до сброса очереди могут потерять
  последние события. Это наблюдение, а не транзакционный журнал бизнес-операций.
- Числа уникальных на обзоре — сумма уникальных каждого бота, с явной подписью.
- Порог heartbeat означает «нет связи», а не подтверждённое завершение.
- Подробные события хранятся в пределах настроенного срока; тест нагрузки на
  короткой истории не доказывает скорость запросов на годовой базе.

Ориентиры: [SQLite WAL](https://www.sqlite.org/wal.html),
[Node.js child_process](https://nodejs.org/api/child_process.html),
[Electron context isolation](https://www.electronjs.org/docs/latest/tutorial/context-isolation).

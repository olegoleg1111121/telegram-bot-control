# Логи, ресурсы и автоматический перезапуск

## Ошибка при запуске до подключения SDK

При неудачном запуске раскройте **«Вывод команды запуска»** в карточке бота:
в 0.5.1 он открывается автоматически. Здесь сохраняются stdout/stderr программы
и подготовительных команд, в том числе ModuleNotFoundError, SyntaxError и ошибки
конфигурации до вызова `start(...)`. Для старых попыток, сделанных до 0.5.1,
вывода нет — повторите запуск для получения причины. Подробности можно скопировать.

Сохраняется хвост до 32 768 символов на запуск; строки длиннее 8 192 символов
пропускаются целиком, очередь вывода ограничена. Хвосты хранятся для последних
50 запусков и активных процессов. Значения секретных переменных окружения,
включая переданные через env-файл, и типичные секреты маскируются до сохранения.
Этот вывод существует отдельно от интеграции logging/Loguru и доступен даже
при неработающем боте. У stdout/stderr разных потоков нет строгого общего порядка.

Если приложение открыто ярлыком, оно не наследует временные переменные ранее
закрытого PowerShell. Для такого бота выберите его локальный env-файл в профиле
или настройте загрузку конфигурации самим ботом. Для остальных проектов поле
env-файла и список обязательных переменных остаются необязательными.

## Существующий Python logging

Не меняйте привычную настройку своего логгера. После создания monitor подключите
дополнительный обработчик:

Сначала выполните существующую настройку logging, затем подключайте обработчик.
Это также сохраняет обычное поведение `basicConfig`, которое не перенастраивает
уже существующие root handlers без `force=True`.

```python
monitor.capture_logs()  # корневой logging, INFO и выше
```

Или укажите `capture_logs=True` в `start(...)`. Используйте один из этих способов.
Файловые/консольные обработчики, форматтеры, уровни и propagate остаются прежними.
Если приложение уже настроило logging на INFO, новые INFO-записи попадут и в панель.
Если уровень самого логгера WARNING, подключение обработчика не включает INFO.
Записи DEBUG можно включить через `monitor.capture_logs(level="DEBUG")`, настроив
также уровень своего логгера.

Для изолированного логгера с `propagate=False`:

```python
monitor.capture_logs("my_bot", level="INFO")
```

Не подключайте одновременно корневой и дочерний обработчик к одному потоку с
propagate=True: это приведёт к двум копиям. Регистрирование на том же объекте
monitor и том же логгере повторно не добавляет обработчик.

Используются стандартные [logging handlers](https://docs.python.org/3/library/logging.html#handler-objects).
Вызов логгера передаёт данные в ограниченную очередь, а SQLite записывается в
отдельном потоке. Поддерживаются вызовы из потоков приложения. При штатном закрытии
monitor обработчик снимается, прежние обработчики продолжают работать.

## Существующий Loguru

```python
from loguru import logger

sink_id = logger.add(monitor.loguru_sink, level="INFO")
# При штатном завершении вашего приложения:
# logger.remove(sink_id)
```

Это дополнительный sink. Существующие sinks остаются на месте. Loguru не добавлен
в обязательные зависимости панели; он уже должен быть в окружении бота. Если вы
настроили перенаправление Loguru в logging, подключите только один адаптер, чтобы
не дублировать записи. Исторические файлы логов не импортируются: сбор начинается
после подключения обработчика/sink.

Сохраняются время, числовой уровень, имя логгера, текст, источник и traceback
исключения без локальных переменных и строк исходного кода. Токен подключённого
бота и типичные записи token/password/secret/api_key маскируются до записи.
Произвольный текст логов может содержать персональные данные: не логируйте
сообщения пользователей и неизвестные библиотеке секреты. Панель не пытается
считать такие записи обычными входящими событиями или ошибками middleware.

В карточке бота → **Логи** доступны поиск по тексту/имени, минимальный уровень,
новые записи каждые три секунды и страницы по 100 записей. На старых страницах
автообновление приостанавливается. В настройках задаётся срок хранения; дополнительно
действует ограничение последних 20 000 записей на бота даже при выборе «не удалять».
Одна запись ограничена 4 000 символами текста и 16 000 символами traceback.

## Ресурсы конкретного процесса

Обновлённая библиотека измеряет собственный PID: CPU, RSS и количество потоков.
Это не потребление всей машины, панели, launcher или дочерних процессов бота.
Измерения идут внутри бота и сохраняются даже при закрытой панели. Используются
process CPU time и [RSS psutil](https://psutil.io/).

- 100% CPU соответствует одному логическому ядру; многопоточный процесс может
  показывать больше 100%. Первый CPU-замер пустой, пока нет предыдущего интервала.
- RSS — физическая память процесса. Это не сумма памяти всех потомков и не USS.
- Если несколько ботов находятся в одном Python-процессе, показания относятся ко
  всему общему процессу. Интерфейс показывает предупреждение; разделить память
  между ботами на уровне ОС нельзя.
- График не соединяет разные сессии и большие промежутки без замеров. После остановки
  показан последний сохранённый замер с соответствующей подписью.
- Срок хранения и интервал (по умолчанию 7 дней и 5 секунд) задаются в настройках.
  Ограничение — последние 150 000 замеров на бота. На Android доступ зависит от ОС.

## Автоперезапуск

Карточка бота → **Настроить запуск** → **Перезапускать при завершении с ошибкой**.
Настройка выключена по умолчанию и начинает действовать при следующем запуске из
панели. Для уже запущенного вручную процесса сначала нужен запуск через панель.

По умолчанию разрешены пять повторных попыток, задержки 2, 4, 8, 16, 32 секунды,
с потолком 60 секунд. После 300 секунд стабильной работы счётчик последовательных
неудач сбрасывается. Лимиты и задержки меняются отдельно для каждого бота.

Код выхода 0 считается нормальным завершением. Ошибка обработчика, которую бот
перехватил и продолжил работу, не вызывает перезапуск. «Остановить» отменяет
ожидающий перезапуск. После исчерпания лимита нужно проверить логи и запустить
бота вручную. Подготовительные команды повторяются при каждой попытке, поэтому
они должны допускать повторное выполнение. Ошибку создания процесса/конфигурации
нужно исправить вручную.

За запущенным ботом следит его отдельный launcher без слушающего порта: закрытие
панели или браузера не отменяет выбранную политику. Это не установка службы и не
автозапуск после перезагрузки сервера. Управлять тем же ботом одновременно через
systemd, Windows service и эту политику не следует: выберите одного владельца запуска.
